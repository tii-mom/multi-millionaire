# Project 72H / Millionaire Path 产品需求文档

## 0. 方法论

本文用两个视角重新整理产品：

- 第一性原理：不从「别人怎么做 DeFi」「别人怎么做邀请返佣」出发，而是回到资产、用户、链上摩擦、信任和传播的不可压缩事实，再推导产品。
- 默会知识：社区 FOMO、信任、身份感、传播冲动很难完全写成规则。产品必须通过可体验的界面、节奏、仪式、示范海报、排行榜和运营动作，让用户「看懂、模仿、参与、传播」。

本文不是营销承诺。任何真实资产、奖励、解锁都必须以合约和链上记录为准。

## 1. 第一性原理：不可压缩事实

### 1.1 资产事实

- `72H` 是真实代币，合约已经部署。
- 用户存入的 `72H` 进入锁仓合约托管，不是前端模拟。
- 存入、解锁、提现、领取奖励都属于链上操作。
- 平台默认不补贴 gas，所有链上 gas 费由用户自己承担。

### 1.2 解锁事实

- 存款是锁仓。
- 解锁不是固定时间自动释放，而是由管理员手动上传 `72H` 价格后触发判断。
- 管理员上传价格是中心化信任点，产品必须明确披露。
- 最终可解锁状态应以合约规则为准，前端只能展示和辅助判断。

### 1.3 用户事实

- 新用户最怕的不是没有收益故事，而是第一步成本高：买币、连钱包、授权、付 gas、理解规则。
- 老用户愿意传播的前提是内容能显示身份、排名、早期参与感和团队优势。
- 用户会被真实稀缺驱动，但虚假收益承诺会带来信任和合规风险。
- 大多数用户不会读完整规则，所以关键规则必须在交易前、海报上、奖励页和解锁页重复出现。

### 1.4 增长事实

- 单纯分享按钮不能证明真实曝光，也不能证明有效增长。
- 可验证的增长结果是：被邀请用户进入、绑定邀请关系、连接钱包、完成有效锁仓。
- 病毒传播需要低门槛入口，但真实奖励必须绑定高质量行为。
- 刷点击的成本很低，刷有效链上锁仓的成本高得多。

## 2. 产品结论

### 2.1 一句话定位

Project 72H 是一个围绕真实 `72H` 代币的社交化锁仓增长系统：用户锁仓 72H，加入 Squad，参与 72 小时波次冲刺，通过可分享身份、团队排名和有效邀请推动增长。

### 2.2 不做什么

- 不承诺用户一定成为百万富翁。
- 不承诺固定收益、无风险收益或保底回报。
- 不把 `Rush Pass`、`Heat`、排行榜或海报包装成真实资产。
- 不按点击分享按钮直接发真实 `72H` 奖励。
- 不隐藏管理员手动上传价格这一中心化机制。

### 2.3 产品核心张力

产品必须同时满足两件事：

- 低门槛传播：用户不连接钱包也能先领取 Pass、加入波次、分享邀请。
- 高质量结算：真实奖励、真实排名、真实解锁必须回到链上锁仓和合约状态。

由此推导出核心结构：`Rush Pass` 负责传播，`Lock 72H` 负责真实参与，`Squad` 负责社会压力，`Admin Price` 负责解锁判断，`Referral Reward` 负责有效增长结算。

## 3. 默会知识：产品如何让用户自然 FOMO

Michael Polanyi 的默会知识理论提醒我们：很多实践能力无法完全靠文字说明传递。社区产品尤其如此，FOMO 不是一句文案，而是用户在反复看到倒计时、队友动作、排名变化、海报扩散、群内截图后形成的参与直觉。

### 3.1 需要被设计出来的默会知识

- 用户要直觉理解：现在是一个 72 小时窗口，错过会失去当前波次身份。
- 用户要直觉理解：先领取 Pass 没成本，激活才需要钱包和锁仓。
- 用户要直觉理解：分享可以带来 Heat 和队伍热度，但真实奖励来自有效锁仓。
- 用户要直觉理解：管理员价格会影响解锁，价格不是实时交易所自动价。
- 用户要直觉理解：gas 是自己承担，低额奖励可以先累计后领取。

### 3.2 传递默会知识的产品手段

- 用倒计时、波次编号、席位、队伍进度条让用户感到「活动正在发生」。
- 用默认海报模板、默认邀请文案、默认 Squad 名片降低分享决策成本。
- 用「Pending -> Activated」状态让用户自然学会 off-chain 和 on-chain 的区别。
- 用交易前提示、状态标签和历史记录反复教育用户 gas、价格、锁仓和解锁规则。
- 用公开排行榜和队伍差距提示，让用户模仿头部队伍的行为。

### 3.3 运营必须沉淀的默会知识

- 哪类海报让用户更愿意转发。
- 哪类波次名称让用户更容易理解和参与。
- 哪个最低锁仓门槛能兼顾低门槛和反刷。
- 哪种排行榜更能刺激团队长拉人。
- 哪些异常模式通常是刷子。

这些不能只靠 PRD 一次写死，需要通过每个 72 小时波次复盘，沉淀到运营手册、文案库、风控规则和产品迭代里。

## 4. 核心产品结构

### 4.1 Deposit / Lock

用户完成真实链上锁仓。

- 展示钱包地址、网络、`72H` 余额。
- 首次锁仓前完成 `approve`。
- 用户输入锁仓数量，支持 `Max`。
- 提交锁仓交易，将 `72H` 转入锁仓合约。
- 显示交易状态：待签名、广播中、确认中、成功、失败。
- 展示每笔锁仓数量、锁仓价格、目标解锁价格、当前管理员价格、可解锁状态。
- 存入、解锁和提现的 gas 均由用户承担。

### 4.2 Admin Price / Unlock

管理员上传价格，系统根据合约规则刷新可解锁状态。

- 前端展示当前管理员上传价格、更新时间和上传凭证。
- 后台记录上传者、价格、时间、交易哈希或签名凭证。
- 用户看到每笔锁仓距离解锁还差多少。
- 满足解锁条件后，用户自行发起解锁或提现交易，并承担 gas。
- 如果合约支持，价格上传应优先走链上事件；如果暂时走后端，必须保留审计记录。

### 4.3 Squad

Squad 是传播和社会压力单元。

- 用户可以创建或加入 Squad。
- 每个 Squad 有唯一邀请链接。
- 展示团队总锁仓量、团队当前美元价值、成员数、激活 Pass 数、Heat 分。
- 展示团队目标和距离下一档徽章的差距。
- 团队长可以设置目标、复制邀请文案、下载团队海报。

### 4.4 Share / Referral

分享只负责传播链路，真实奖励按有效锁仓结算。

- 用户生成个人海报、Squad 海报和邀请链接。
- 邀请关系采用首次绑定原则，一个钱包只绑定第一个有效邀请人。
- 被邀请人完成有效锁仓后，邀请人才进入奖励待结算。
- 奖励通过 `Pending -> Claimable -> Claimed` 状态流转。
- 用户领取奖励时自行支付 gas；如果预计 gas 高于奖励价值，前端提示用户累计后再领取。

### 4.5 智能合约规划

已部署的 `72H` 代币合约不计入新增业务合约。围绕本产品，新增合约按三层拆分：

- `72HLockVault`：必需合约，负责接收用户存入的 `72H`、记录锁仓、判断可解锁状态、处理解锁和提现。
- `AdminPriceOracle` 或 `PriceController`：推荐独立合约，负责管理员上传价格、记录价格版本、上传时间、上传者和事件，供锁仓合约读取。
- `RewardDistributor`：推荐独立合约，负责邀请奖励预算、可领取奖励、领取状态和奖励发放。

MVP 如果追求最快上线，可以先把价格上传逻辑合并进 `72HLockVault`，奖励先由后端记账和人工审核。正式上线建议使用三合约架构，把用户锁仓资产、管理员价格、营销奖励拆开，降低单点风险和升级成本。

不建议上链的模块：

- `Rush Pass`。
- `Squad`。
- `Heat`。
- 邀请点击。
- 波次倒计时。

这些模块 MVP 阶段应放在后端数据库中，因为规则会频繁调整，链上化会增加 gas 成本和迭代阻力。真实奖励仍通过有效链上锁仓触发，避免 off-chain 热度直接兑换真实资产。

## 5. 新增增长功能：72H Rush Pass

### 5.1 功能定义

`72H Rush Pass` 是低门槛传播入口，不是资产、不是空投承诺、不是收益凭证。

用户无需连接钱包即可领取 `Pending Rush Pass`，加入一个 72 小时波次，获得个人邀请链接和可分享身份。只有连接钱包并完成最低有效锁仓后，Pass 才升级为 `Activated Rush Pass`，并计入真实排名、真实奖励和 Squad 贡献。

### 5.2 用户流程

1. 老用户分享 Rush Pass 链接或海报。
2. 新用户打开落地页，看到邀请人、Squad、波次倒计时和当前热度。
3. 新用户输入昵称领取 `Pending Rush Pass`，无需钱包、无需 gas。
4. 新用户获得自己的邀请链接，可以继续分享。
5. 用户连接钱包并完成最低有效锁仓。
6. Pass 升级为 `Activated Rush Pass`。
7. 邀请人进入奖励待结算，Squad 排行更新。

### 5.3 FOMO 机制

- 每 72 小时开启一个 `Wave`。
- 每个 Wave 有倒计时、编号、排行榜和阶段徽章。
- `Pending Rush Pass` 有有效期，例如 24 小时；过期未激活则 Heat 权重衰减。
- `Activated Rush Pass` 可以有波次限量或排名权益，制造真实稀缺。
- 首页展示「本波次剩余时间」「你的 Squad 距离 Top 10 差多少」「还有多少人已激活」。
- 海报展示波次、排名、Squad 和倒计时，不展示收益承诺。

### 5.4 Heat 机制

`Heat` 是传播热度，不是代币奖励。

- 邀请新用户领取 Pending Pass 增加 Heat。
- 邀请新用户激活 Pass 增加更多 Heat。
- Heat 可以影响展示排名、徽章、海报样式和 Squad 热度。
- Heat 不能直接兑换真实 `72H`。
- 真实 `72H` 奖励只按有效锁仓计算。

### 5.5 低门槛策略

- 领取 Pass 不需要钱包。
- 分享和加入 Squad 不需要 gas。
- 最低有效锁仓门槛应足够低，让用户能尝试；但不能低到刷子无成本。
- 低额用户也应获得身份反馈，例如波次徽章、Squad 贡献、海报升级。
- 高额用户获得更强贡献权重，但不能让低额用户完全失去参与感。

## 6. 分享奖励与防刷

### 6.1 奖励触发条件

一次邀请奖励必须同时满足：

- 邀请人已生成有效邀请链接。
- 被邀请人首次进入时携带有效邀请码。
- 被邀请钱包此前未绑定其他邀请人。
- 被邀请人完成至少一笔链上锁仓。
- 锁仓数量达到最低有效门槛 `minValidDeposit`。
- 锁仓交易达到确认数要求，例如 12 个区块确认。
- 观察期结束后未被风控标记异常。

### 6.2 推荐奖励公式

MVP 使用单层邀请奖励，不做多级返佣。

- 邀请人奖励：`有效锁仓数量 * 1%`，设置单笔上限、每日上限和活动总预算。
- 被邀请人奖励：首笔有效锁仓获得 `0.3% - 0.5%` 新用户奖励。
- 每个被邀请钱包只能触发一次首笔奖励。
- 奖励先进入 `Pending`，观察期和风控通过后进入 `Claimable`。
- 用户领取奖励时承担 gas；低额奖励提示累计后领取。

如果真实代币预算有限，先把奖励记为 `points` 或 `pending 72H`，由管理员定期审核后批量发放。自动化阶段可考虑奖励合约或 Merkle Distributor。

### 6.3 防刷规则

- 禁止自邀请。
- 一个钱包只能绑定第一个有效邀请人。
- 同一设备、IP、浏览器指纹短时间大量领取 Pass 时降权或进入人工审核。
- 多个被邀请钱包由同一地址集中转入 gas 或 `72H` 时进入人工审核。
- 同一邀请人每日待结算奖励数量和金额设上限。
- 低于最低锁仓门槛的锁仓不计奖励。
- 异常钱包、设备、IP、邀请关系可被管理员加入黑名单。
- `Heat` 与真实奖励分离，刷点击最多影响轻量展示，不影响真实代币。

## 7. MVP 范围

### 7.1 必做

- 钱包连接、网络校验、地址展示。
- `72H` 余额读取和授权。
- 锁仓交易提交和状态展示。
- 管理员价格展示和锁仓可解锁状态展示。
- Rush Pass 领取、邀请链接、波次倒计时。
- Squad 创建、加入、排行榜。
- 分享海报、复制邀请文案。
- 有效邀请绑定和奖励状态展示。
- gas 由用户承担的交易前提示。

### 7.2 暂缓

- 多级返佣。
- 自动化复杂奖池。
- NFT 徽章。
- 多链支持。
- KOL 专属后台。
- 完整运营后台。
- 链上全自动价格治理。

## 8. 页面需求

### 8.1 Home

- 当前 Wave 倒计时。
- 我的锁仓总量、当前价值、目标进度。
- 当前管理员价格和更新时间。
- 距离解锁条件还差多少。
- 快速锁仓入口。
- gas 由用户承担提示。

### 8.2 Lock

- 钱包余额。
- 授权状态。
- 锁仓输入框和 `Max`。
- 交易状态时间线。
- 锁仓记录列表。
- 可解锁操作入口。

### 8.3 Squad

- Squad 名称、排名、成员数。
- Squad 总锁仓、总 Heat、激活 Pass 数。
- 距离下一档徽章或 Top 10 的差距。
- 成员贡献榜。
- 邀请队友按钮。

### 8.4 Rush Pass / Share

- 我的 Pass 状态：未领取、Pending、Activated、Expired。
- Wave 倒计时和个人排名。
- Heat 分和来源。
- 个人邀请链接。
- 海报生成、复制文案、下载图片、系统分享。
- 规则提示：Pass 不是资产，奖励按有效锁仓结算。

### 8.5 Rewards

- Pending Reward。
- Claimable Reward。
- Claimed History。
- 预计 gas 提示或钱包弹窗提示。
- 奖励低于 gas 成本时建议累计。

## 9. 数据与接口

### 9.1 前端需要的数据

- 当前钱包地址、网络、`72H` 余额。
- `72H` 代币合约地址、锁仓合约地址、目标 Chain ID。
- 用户锁仓记录：数量、锁仓价格、目标解锁价格、当前价格、状态、交易哈希。
- 管理员上传价格：价格、上传者、更新时间、交易哈希或签名凭证。
- Rush Pass：波次 ID、状态、昵称、邀请人、Heat、过期时间、激活钱包。
- Squad：名称、目标、成员数、邀请码、排名、Heat、总锁仓。
- 邀请关系：邀请人、被邀请人、绑定时间、来源链接、风控状态。
- 奖励状态：Pending、Claimable、Claimed、Rejected。

### 9.2 后端或链上需要提供

- ERC-20 读写接口：余额、授权、事件。
- 锁仓合约读写接口：存入、解锁、提现、锁仓记录查询。
- 管理员价格上传接口或合约方法。
- 用户、Squad、Rush Pass 和邀请关系索引。
- 奖励规则和领取接口。
- 风控记录和人工审核接口。

### 9.3 集成前需要提供

- `72H` 代币合约地址。
- 锁仓合约地址。
- 所在网络和 Chain ID。
- 合约 ABI，或已验证区块浏览器链接。
- 代币精度 `decimals`。
- 管理员价格上传方法、价格精度和事件名。
- 锁仓、解锁、提现相关方法和事件名。
- 是否已有测试网合约或开发钱包。

## 10. 风控与合规底线

- 所有收益相关文案使用「奖励」「活动激励」「邀请奖励」，避免固定收益表达。
- 页面必须提示代币价格波动风险。
- 页面必须提示管理员上传价格是中心化机制。
- 分享海报不能包含保底收益、保证暴富、确定回报等表达。
- Rush Pass 只能表达活动资格、身份和邀请入口，不能表达为空投承诺或资产。
- 用户领取奖励、存入、解锁、提现的 gas 均由用户承担。
- 如果奖励用户推广或邀请，文案应提示用户披露激励关系。

## 11. 默会知识运营机制

为了把无法完全写成规则的增长经验沉淀下来，每个 Wave 结束后必须复盘：

- 哪张海报分享率最高。
- 哪句邀请文案带来最多 Pass 领取。
- 哪个 Squad 的转化率最高，原因是什么。
- Pending Pass 到 Activated Pass 的最大掉点在哪里。
- 哪些风控规则误伤了真实用户。
- 哪些刷量模式需要加入黑名单或降权。
- 下一轮 Wave 应该调整哪个变量：门槛、倒计时、徽章、奖励、排行榜。

输出沉淀到三份资产：

- 运营 Playbook：波次命名、群内节奏、KOL 话术、海报模板。
- 风控 Playbook：异常模式、处理方式、证据字段。
- 产品 Backlog：每轮实验后的明确功能改动。

## 12. 关键待确认问题

- 解锁条件到底是「当前管理员价格 >= 用户目标解锁价」，还是「用户锁仓资产价值达到某个美元目标」？
- 每笔锁仓是否允许用户设置不同目标价格？
- 管理员上传价格是在合约内完成，还是由后端记录后前端读取？
- 上传价格是否需要多签、延迟生效或二次确认？
- 奖励来源是新增代币、项目方预算、手续费返还，还是积分？
- Squad 排行按锁仓数量、美元价值、激活人数、Heat，还是综合积分？
- 是否允许提前解锁？如果允许，惩罚是什么？
- Rush Pass 每个 Wave 是否限制总领取数，还是只限制 Activated 名额？
- 最低有效锁仓门槛是多少，是否按管理员价格动态调整？
- 是否需要 KYC、地区限制或更强风险提示？
